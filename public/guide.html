Mode guide

7 input modes, mapped to situations

Same request, same generator — only what you feed the model changes. This page maps each mode to what it produces, where it breaks, and the rule for when to reach for it.

Simulated generator, honest limits. The modes are modeled by a deterministic mock, not a real model — it exists so the scoring axes are measurable. The failure patterns are real; the exact numbers are illustrative.

What this demo proves

A bare text brief produces a plausible page where almost every value is off-system — random colors, random spacing, failed contrast. Feeding the same request design tokens or a component library pins the output on-system, and a browser-verify loop repairs what even good inputs miss. Run Run all in the lab and compare the columns.

Generation modes

Modes 1–5: what you feed it

1 · Text-describe

A one-line brief. The model invents the layout order and every single value — which is why the output is generic by construction.

Use for: throwaway mockups where consistency does not matter.

2 · Screenshot imitation

A reference image copies structure well — elements land in the right places — but the system is guessed: near-right colors, arbitrary spacing and radii.

Use for: copying a layout's shape, never its design system.

3 · Design tokens

Palette, spacing scale, radii, and type scale pasted into the prompt. Every value lands on-system — though independent foreground/background picks can still fail contrast.

Use for: the default mode for real product work.

4 · Component library

"Use only these variants." The strongest fidelity lever: the model cannot invent off-system pieces because the pieces do not exist. Scores 100% on tokens and accessibility in the lab.

Use for: production screens.

5 · Spec-first wireframe

A layout contract — slots, order, type hierarchy — written before any pixels. Structure errors get caught at the cheapest moment to fix them.

Use for: complex flows where layout mistakes are expensive.

Why modes beat models

Swapping the model changes taste; swapping the input changes the constraints. In the lab, the generator never changes — only the input mode does — and the overall score climbs from coin-flip to 1.00.

Rule: pick the mode for the situation, then pick the model.

Process modes

Modes 6–7: what you check it with

6 · Browser-verify loop

Generate → render → score mechanically (contrast, hit targets, layout order) → fix the worst axis → re-score. The loop in the lab starts from a raw text-mode spec and climbs to ≥0.9 within a few rounds.

Use for: anything interactive or responsive.

7 · Screenshot-diff check

Once a UI is approved, freeze it as a baseline. Re-render after any change — model update, refactor, prompt tweak — and diff element by element. Drift becomes a failed check instead of a silent redesign.

Use for: guarding an approved UI forever after.

Architecture

How the lab is built

Inspect the evidence

Two request fixtures ship in examples/ — a settings page and a checkout modal — plus a frozen approved baseline for the diff check.

Limits

What this demo does not claim

  • The generator is a deterministic simulation, not a real model — it makes the failure modes measurable, not probabilistic.
  • Scores are proxies: token compliance is not visual quality, and the a11y checks cover contrast, font size, and target size only — not keyboard flow or screen-reader semantics.
  • Layout match checks element order, not real pixel geometry or breakpoints.
  • The verify loop's fixers are deterministic repairs; a real agent's fix can introduce new defects — keep the loop bounded.
